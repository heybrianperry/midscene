<rule_activation id="e36bf292-5924-4229-b89c-30b4bf1265d8" title="Adopt IndexedDB as Client-Side Cache Layer for Logging and State Persistence: Logging Utilities Implement" applies_to="**/*">
These rules are ALWAYS ACTIVE for all client-side applications, Chrome extensions, browser-based tools, and Progressive Web Applications requiring persistent logging and state management.
</rule_activation>

### Rules

- **R-INDEXEDDB-001** SHOULD: Logging utilities SHOULD implement structured data schemas with indexes on timestamp and severity fields for efficient querying.

### Verify

```bash
# Detect IndexedDB usage patterns in client-side code
grep -r "indexedDB\|IndexedDB\|IDBDatabase" apps/ packages/ --include="*.ts" --include="*.tsx" --include="*.js"

# Verify database operations and transactions
grep -r "openDatabase\|createObjectStore\|transaction" apps/ packages/ --include="*.ts" --include="*.tsx"

# Run tests for IndexedDB, caching, and logging storage
npm test -- --grep "IndexedDB|cache.*persist|logging.*storage"
```

**Accept when:**
- All client-side logging and caching implementations use IndexedDB utilities with proper async/await error handling
- IndexedDB implementations include cleanup policies and quota management mechanisms
- Code review confirms no synchronous localStorage usage for large data or logging purposes in browser extension contexts
- Structured logging schemas include indexes on timestamp, severity level, and component name
- Database versioning (onupgradeneeded) is implemented for schema migrations
- Automatic cleanup mechanisms are in place using periodic background tasks

<enforcement>
Claude Code MUST NOT skip or defer verification. All client-side logging and state persistence implementations MUST comply with IndexedDB adoption requirements. Violations require architecture team review and justification. Security team approval is required for exceptions involving sensitive data handling.
</enforcement>
