<rule_activation id="b5aa1a88-0bc0-4203-9f98-7980eeb6b307" title="Adopt Client-Side Cache Layer for Public API State Management: Cache Implementations Provide" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files implementing public API client-side caching, particularly in visualizer, playground, and blackboard components using browser storage APIs.
</rule_activation>

### Rules

- **R-CACHE-001** SHOULD: Cache implementations SHOULD provide fallback mechanisms when storage quota is exceeded or unavailable

### Verify

```bash
# Verify IndexedDB, localStorage, or sessionStorage usage patterns in cache/storage contexts
grep -r 'IndexedDB\|localStorage\|sessionStorage' packages/*/src --include='*.ts' --include='*.tsx' | grep -i 'cache\|storage\|provider'

# Verify cache TTL and expiration logic is implemented
grep -r 'cache.*TTL\|time.*to.*live\|expir' packages/*/src --include='*.ts' --include='*.tsx'

# Verify storage provider abstractions exist
grep -r 'class.*StorageProvider\|interface.*Cache' packages/*/src --include='*.ts' --include='*.tsx'
```

**Accept when:**
- All public API client implementations include a documented cache layer using browser storage APIs
- Cache implementations include explicit TTL configuration and invalidation logic
- Storage provider abstractions exist to decouple cache implementation from consumer code
- Fallback mechanisms are implemented for storage quota exceeded scenarios
- Cache keys follow consistent naming convention: 'api:version:endpoint:params'
- Cache metadata (timestamp, version, TTL) is stored alongside cached data

<enforcement>
Claude Code MUST verify all cache layer implementations against these rules. Violations must be flagged for revision. Exceptions require approval from API Architecture Team and Security Team for sensitive data scenarios.
</enforcement>
