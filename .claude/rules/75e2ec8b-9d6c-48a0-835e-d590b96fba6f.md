<rule_activation id="75e2ec8b-9d6c-48a0-835e-d590b96fba6f" title="Sanitize User Input in Logging Statements to Prevent Log Injection: Ansi Escape Sequences" applies_to="**/*">
These rules are ALWAYS ACTIVE for all logging operations that include user-controlled input or external data sources.
</rule_activation>

### Rules

- **R-LOG-001** MUST: ANSI escape sequences and control characters MUST be stripped or escaped from user input before logging.

### Verify

```bash
# Detect unsanitized logging patterns
grep -r 'console\.log\|logger\.' packages/ | grep -v 'sanitize\|escape\|safe' | head -20

# Run security tests for log injection vulnerabilities
npm run test:security -- --grep 'log injection'

# Lint for unsanitized logging violations
eslint packages/ --rule 'no-unsanitized-logging: error' --format json
```

**Accept when:**
- All logging statements that include user input or external data pass through sanitization functions
- Security test suite includes log injection test cases that verify newlines, control characters, and ANSI codes are properly escaped
- Static analysis or linting rules flag unsanitized logging calls during CI/CD pipeline
- Centralized sanitization utilities (e.g., sanitizeForLog() function) handle common injection vectors including newlines, carriage returns, ANSI codes, and format specifiers
- Logging wrappers or new wrapper functions automatically sanitize parameters before passing to underlying log libraries
- Clear naming conventions distinguish sanitized logging methods (e.g., logSafe() vs. logRaw())

<enforcement>
Claude Code MUST NOT skip or defer verification. Static analysis and security test suite MUST pass before accepting logging implementations. Code review MUST explicitly verify input sanitization in all logging statements containing user input or external data.
</enforcement>
