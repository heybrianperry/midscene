<rule_activation id="9f9ccbe7-4da8-493e-9754-0a004a1c7fad" title="Sanitize User Input in Logging Statements to Prevent Log Injection: Implementations Truncate Excessively" applies_to="**/*">
These rules are ALWAYS ACTIVE for all logging operations that include user-controlled input or external data sources.
</rule_activation>

### Rules

- **R-LOG-001** MAY: Implementations MAY truncate excessively long input values to prevent log flooding attacks.

### Verify

```bash
# Detect unsanitized logging patterns
grep -r 'console\.log\|logger\.' packages/ | grep -v 'sanitize\|escape\|safe' | head -20

# Run security tests for log injection vulnerabilities
npm run test:security -- --grep 'log injection'

# Lint for unsanitized logging calls
eslint packages/ --rule 'no-unsanitized-logging: error' --format json
```

**Accept when:**
- All logging statements that include user input or external data pass through sanitization functions
- Security test suite includes log injection test cases that verify newlines, control characters, and ANSI codes are properly escaped
- Static analysis or linting rules flag unsanitized logging calls during CI/CD pipeline

<enforcement>
Claude Code MUST NOT skip or defer verification. All logging statements containing user-controlled input or external data sources MUST be sanitized before being written to logs. Violations MUST be caught by automated static analysis in CI/CD and blocked from merge.
</enforcement>
