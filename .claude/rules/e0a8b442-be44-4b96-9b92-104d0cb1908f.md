<rule_activation id="e0a8b442-be44-4b96-9b92-104d0cb1908f" title="Standardize Environment Variable Configuration for Runtime Secrets Management: Environment Variable Values" applies_to="**/*">
These rules are ALWAYS ACTIVE for all runtime components that require configuration or secrets management, including CLI tools, browser automation agents, device controllers, and test suites.
</rule_activation>

### Rules

- **R-ENV-001** MUST_NOT: Environment variable values containing secrets MUST NOT be logged, printed to console, or included in error messages in production environments.

### Verify

```bash
# Count process.env usage in non-test files
grep -r 'process\.env\.' --include='*.ts' --include='*.js' | grep -v 'test' | wc -l

# Detect hardcoded secrets not using process.env
grep -r "['\"](API_KEY|TOKEN|SECRET|PASSWORD)['\"]\s*:\s*['\"]" --include='*.ts' --include='*.js' | grep -v 'process.env' | wc -l

# Verify .env files with secrets are in .gitignore
find . -name '.env' -not -path '*/node_modules/*' | xargs grep -l 'API_KEY|TOKEN|SECRET' 2>/dev/null | while read f; do grep -q "^$(basename $f)$" .gitignore || echo "$f not in gitignore"; done
```

**Accept when:**
- All sensitive configuration values (API keys, tokens, passwords) are accessed via process.env rather than hardcoded strings
- No .env files containing secrets are committed to version control (verified by .gitignore entries)
- Each package has documentation listing required environment variables with descriptions and example values
- Configuration modules validate required environment variables at startup and provide clear error messages for missing values

<enforcement>
Claude Code MUST verify that environment variable secrets are never logged, printed, or exposed in error messages. Verification is mandatory before accepting any configuration or secrets management implementation.
</enforcement>
