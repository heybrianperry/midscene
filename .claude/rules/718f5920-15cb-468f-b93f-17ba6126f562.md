<rule_activation id="718f5920-15cb-468f-b93f-17ba6126f562" title="Adopt Client-Side Cache Layer for Public API State Management: Sensitive Authentication Tokens" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files implementing client-side cache layers for public API state management.
</rule_activation>

### Rules

- **R-CACHE-001** MUST_NOT: Sensitive authentication tokens or personally identifiable information MUST NOT be stored in client-side caches without encryption.

### Verify

```bash
# Verify IndexedDB, localStorage, and sessionStorage usage patterns
grep -r 'IndexedDB\|localStorage\|sessionStorage' packages/*/src --include='*.ts' --include='*.tsx' | grep -i 'cache\|storage\|provider'

# Verify cache TTL and expiration logic
grep -r 'cache.*TTL\|time.*to.*live\|expir' packages/*/src --include='*.ts' --include='*.tsx'

# Verify storage provider abstractions
grep -r 'class.*StorageProvider\|interface.*Cache' packages/*/src --include='*.ts' --include='*.tsx'
```

**Accept when:**
- All public API client implementations include a documented cache layer using browser storage APIs
- Cache implementations include explicit TTL configuration and invalidation logic
- Storage provider abstractions exist to decouple cache implementation from consumer code
- Sensitive authentication tokens are explicitly excluded from client-side caches or encrypted with documented key management
- Cache metadata (timestamp, version, TTL) is included alongside cached data for effective invalidation

<enforcement>
Claude Code MUST verify all client-side cache implementations against R-CACHE-001 before approving changes to public API client code. Violations involving unencrypted sensitive data storage MUST be flagged and rejected.
</enforcement>
