<rule_activation id="043d5535-9396-4c55-9fd7-27e182862c21" title="Standardize Environment Variable Configuration Management Pattern: Direct Process Env" applies_to="**/*">
These rules are ALWAYS ACTIVE for all configuration and environment management code across the codebase.
</rule_activation>

### Rules

- **R-ENV-001** MUST_NOT: Direct process.env access MUST NOT be scattered throughout application code; all access must go through configuration modules

### Verify

```bash
# Count direct process.env access outside configuration modules
grep -r 'process\.env' --include='*.ts' --include='*.js' --exclude-dir=node_modules | grep -v 'common.ts\|config.ts\|env.ts' | wc -l

# Count configuration modules with process.env access
find . -name 'common.ts' -o -name 'config.ts' -o -name 'env.ts' | xargs grep -l 'process\.env' | wc -l

# Check ESLint no-process-env rule violations
npm run lint -- --rule 'no-process-env: error' 2>&1 | grep -c 'process.env'
```

**Accept when:**
- All direct process.env accesses are contained within designated configuration modules (common.ts, config.ts, env.ts)
- Each package with environment dependencies has a dedicated configuration module with typed exports
- Linting rules successfully detect and flag any direct process.env access outside configuration modules
- Configuration modules export typed constants or objects rather than raw environment variables
- Required vs. optional environment variables are documented in package README files

<enforcement>
Claude Code MUST verify this rule is satisfied before accepting configuration or environment management code. Violations MUST be refactored to use centralized configuration modules. Exceptions require tech lead approval and must be documented with TODO comments.
</enforcement>
