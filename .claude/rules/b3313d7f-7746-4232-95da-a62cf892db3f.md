<rule_activation id="b3313d7f-7746-4232-95da-a62cf892db3f" title="Adopt Client-Side Cache Layer for Public API State Management: Cache Providers Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files implementing public API client-side caching and state management across visualizer, playground, and blackboard interfaces.
</rule_activation>

### Rules

- **R-CACHE-001** SHOULD: Cache providers SHOULD use IndexedDB for structured data exceeding 5MB or requiring complex queries.

### Verify

```bash
# Verify IndexedDB and storage API usage patterns in public API client code
grep -r 'IndexedDB\|localStorage\|sessionStorage' packages/*/src --include='*.ts' --include='*.tsx' | grep -i 'cache\|storage\|provider'

# Verify cache TTL and expiration logic implementation
grep -r 'cache.*TTL\|time.*to.*live\|expir' packages/*/src --include='*.ts' --include='*.tsx'

# Verify storage provider abstractions and cache interfaces
grep -r 'class.*StorageProvider\|interface.*Cache' packages/*/src --include='*.ts' --include='*.tsx'
```

**Accept when:**
- All public API client implementations include a documented cache layer using browser storage APIs
- Cache implementations include explicit TTL configuration and invalidation logic
- Storage provider abstractions exist to decouple cache implementation from consumer code
- Cache keys follow consistent naming convention: 'api:version:endpoint:params'
- Cache metadata (timestamp, version, TTL) is included alongside cached data
- Storage quota monitoring and automatic cache pruning are implemented
- Sensitive data is excluded from cache or encrypted appropriately

<enforcement>
Claude Code MUST NOT skip or defer verification of cache layer implementation. All public API client code MUST be reviewed for compliance with R-CACHE-001. Architecture review is mandatory for new API client implementations. Violations are flagged for revision and tracked in technical debt backlog.
</enforcement>
