<rule_activation id="d91f1043-6ab1-4c65-8fbc-bfe419a41b34" title="Adopt Asynchronous Service Manager Pattern for UI Component Lifecycle: Service Managers Implement" applies_to="packages/*/src/**/*.ts,packages/*/src/**/*.tsx">
These rules are ALWAYS ACTIVE for UI components in visualizer, playground, and webdriver packages that manage asynchronous service initialization and lifecycle coordination.
</rule_activation>

### Rules

- **R-ASYNC-001** SHOULD: Service managers SHOULD implement centralized error handling for service initialization failures.

### Verify

```bash
# Detect ServiceManager pattern implementations
grep -r "class.*ServiceManager" packages/*/src --include="*.ts" --include="*.tsx"

# Verify async lifecycle methods exist
grep -r "async.*initialize\|async.*start\|async.*stop" packages/*/src/managers --include="*.ts"

# Check for ServiceManager lifecycle tests
npm run test -- --grep "ServiceManager" --reporter json | jq '.tests[] | select(.title | contains("lifecycle"))'
```

**Accept when:**
- All UI components with multiple async service dependencies use a ServiceManager or equivalent abstraction
- ServiceManager implementations consistently use Promise-based async/await patterns for lifecycle methods (initialize, start, stop, cleanup)
- Code review checklist includes verification of ServiceManager pattern for complex UI components
- Centralized error handling is implemented in all ServiceManager instances
- TypeScript types enforce proper service manager contracts

<enforcement>
Claude Code MUST verify ServiceManager pattern compliance before approving changes to UI components in visualizer, playground, and webdriver packages. Violations MUST be flagged as CI warnings and require architecture team review for exceptions.
</enforcement>
