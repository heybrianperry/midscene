<rule_activation id="7f9208a6-d279-4f5b-8b90-0017d6ea539b" title="Adopt Asynchronous Service Manager Pattern for UI Component Lifecycle: Components That Manage" applies_to="packages/*/src/**/*.ts,packages/*/src/**/*.tsx">
These rules are ALWAYS ACTIVE for UI components in visualizer, playground, and webdriver packages that manage multiple asynchronous services.
</rule_activation>

### Rules

- **R-ASYNC-001** MUST: UI components that manage multiple services MUST use a dedicated ServiceManager or equivalent abstraction to coordinate asynchronous initialization.

### Verify

```bash
# Detect ServiceManager pattern usage in UI components
grep -r "class.*ServiceManager" packages/*/src --include="*.ts" --include="*.tsx"

# Verify async lifecycle methods are Promise-based
grep -r "async.*initialize\|async.*start\|async.*stop" packages/*/src/managers --include="*.ts"

# Check for lifecycle-related tests
npm run test -- --grep "ServiceManager" --reporter json | jq '.tests[] | select(.title | contains("lifecycle"))'
```

**Accept when:**
- All UI components with multiple async service dependencies use a ServiceManager or equivalent abstraction
- ServiceManager implementations consistently use Promise-based async/await patterns for lifecycle methods (initialize, start, stop, cleanup)
- Code review checklist includes verification of ServiceManager pattern for complex UI components
- ServiceManager pattern is documented in design system guidelines with examples from visualizer, playground, and webdriver packages
- TypeScript types enforce proper service manager contracts

<enforcement>
Claude Code MUST NOT skip or defer verification of ServiceManager pattern compliance in UI components. Violations must be flagged as CI warnings and addressed through code review feedback or technical debt tickets.
</enforcement>
