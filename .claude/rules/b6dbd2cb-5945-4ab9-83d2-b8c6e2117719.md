<rule_activation id="b6dbd2cb-5945-4ab9-83d2-b8c6e2117719" title="Adopt IndexedDB as Client-Side Cache Layer for Logging and State Persistence: Worker Scripts Background" applies_to="**/*">
These rules are ALWAYS ACTIVE for all client-side applications, Chrome extensions, browser-based tools, and Progressive Web Applications requiring persistent storage for logging and state management.
</rule_activation>

### Rules

- **R-INDEXEDDB-001** SHOULD: Worker scripts and background processes SHOULD use IndexedDB for cross-context state sharing rather than in-memory storage.

### Verify

```bash
# Search for IndexedDB usage patterns
grep -r "indexedDB\|IndexedDB\|IDBDatabase" apps/ packages/ --include="*.ts" --include="*.tsx" --include="*.js"

# Search for database operations
grep -r "openDatabase\|createObjectStore\|transaction" apps/ packages/ --include="*.ts" --include="*.tsx"

# Run tests for IndexedDB, caching, and logging storage
npm test -- --grep "IndexedDB|cache.*persist|logging.*storage"
```

**Accept when:**
- All client-side logging and caching implementations use IndexedDB utilities with proper async/await error handling
- IndexedDB implementations include cleanup policies and quota management mechanisms
- Code review confirms no synchronous localStorage usage for large data or logging purposes in browser extension contexts
- IndexedDB utility module (e.g., indexedDB.ts) encapsulates database initialization, schema versioning, and common CRUD operations
- Structured logging schemas include indexes on timestamp, severity level, and component name
- Automatic cleanup mechanisms are implemented using periodic background tasks

<enforcement>
Claude Code MUST NOT skip or defer verification. All client-side persistent storage implementations MUST be reviewed against these rules before acceptance. Violations using localStorage for large data or logging MUST be flagged for architecture review.
</enforcement>
