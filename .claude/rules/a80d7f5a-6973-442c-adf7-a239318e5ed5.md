<rule_activation id="a80d7f5a-6973-442c-adf7-a239318e5ed5" title="Adopt Asynchronous Service Manager Pattern for UI Component Lifecycle: Service Managers Prevent" applies_to="packages/*/src/**/*.ts,packages/*/src/**/*.tsx">
These rules are ALWAYS ACTIVE for UI components in visualizer, playground, and webdriver packages that manage asynchronous service initialization and lifecycle coordination.
</rule_activation>

### Rules

- **R-ASM-001** MUST: Service managers MUST prevent race conditions by ensuring dependent services are initialized in correct order.

### Verify

```bash
# Detect ServiceManager pattern usage
grep -r "class.*ServiceManager" packages/*/src --include="*.ts" --include="*.tsx"

# Verify async lifecycle methods
grep -r "async.*initialize\|async.*start\|async.*stop" packages/*/src/managers --include="*.ts"

# Check for lifecycle-related tests
npm run test -- --grep "ServiceManager" --reporter json | jq '.tests[] | select(.title | contains("lifecycle"))'
```

**Accept when:**
- All UI components with multiple async service dependencies use a ServiceManager or equivalent abstraction
- ServiceManager implementations consistently use Promise-based async/await patterns for lifecycle methods (initialize, start, stop, cleanup)
- Code review checklist includes verification of ServiceManager pattern for complex UI components
- ServiceManager pattern is applied across visualizer, playground, and webdriver packages with consistent conventions
- Dependent services are explicitly ordered and initialized sequentially to prevent race conditions

<enforcement>
Claude Code MUST NOT skip or defer verification of ServiceManager pattern compliance. Violations must be flagged as CI build warnings and addressed through code review feedback or technical debt tickets.
</enforcement>
