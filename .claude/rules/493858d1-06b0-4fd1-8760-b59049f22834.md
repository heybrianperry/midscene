<rule_activation id="493858d1-06b0-4fd1-8760-b59049f22834" title="Sanitize User Input in Logging Statements to Prevent Log Injection: User Controlled Input" applies_to="**/*">
These rules are ALWAYS ACTIVE for all logging operations that include user-controlled input or external data sources.
</rule_activation>

### Rules

- **R-LOG-001** MUST: All user-controlled input and external data MUST be sanitized before being written to logs.

### Verify

```bash
# Check for unsanitized logging statements
grep -r 'console\.log\|logger\.' packages/ | grep -v 'sanitize\|escape\|safe' | head -20

# Run security tests for log injection
npm run test:security -- --grep 'log injection'

# Run ESLint with unsanitized logging rule
eslint packages/ --rule 'no-unsanitized-logging: error' --format json
```

**Accept when:**
- All logging statements that include user input or external data pass through sanitization functions
- Security test suite includes log injection test cases that verify newlines, control characters, and ANSI codes are properly escaped
- Static analysis or linting rules flag unsanitized logging calls during CI/CD pipeline
- Centralized sanitization utilities (e.g., sanitizeForLog() function) handle common injection vectors including newlines, carriage returns, ANSI codes, and format specifiers
- Logging methods are clearly documented with naming conventions distinguishing sanitized (e.g., logSafe()) from unsanitized (e.g., logRaw()) approaches

<enforcement>
Claude Code MUST NOT skip or defer verification. All logging statements containing user-controlled input or external data MUST pass through sanitization functions before being written to logs. Violations MUST be flagged during code review and CI/CD pipeline checks MUST fail if unsanitized logging patterns are detected.
</enforcement>
