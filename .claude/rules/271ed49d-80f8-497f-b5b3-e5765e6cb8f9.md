<rule_activation id="271ed49d-80f8-497f-b5b3-e5765e6cb8f9" title="Adopt Event-Driven Logging with Buffered Batch Processing for Data Access Operations" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`. Event-driven logging with buffered batch processing MUST be used for data access operations in performance-sensitive contexts to prevent synchronous I/O blocking.
</rule_activation>

### Rules

- **R-EVLOG-001** MUST NOT: Logging operations MUST NOT introduce synchronous I/O or network calls in the critical path of data access operations in browser extensions, real-time streaming, keepalive mechanisms, or performance-critical data retrieval layers.

- **R-EVLOG-002** MUST: All data access operations in performance-critical paths MUST use buffered logging mechanisms with configurable flush intervals (1-5 seconds for high-frequency events, immediate for errors) rather than synchronous writes.

- **R-EVLOG-003** MUST: Event buffer implementations MUST include configurable flush intervals and maximum size limits with overflow handling (drop oldest or newest events) and circuit breaker patterns for failing log destinations.

- **R-EVLOG-004** MUST: Log events MUST include structured metadata (timestamps, correlation IDs, operation context, component, level, duration) sufficient for distributed tracing and effective querying.

- **R-EVLOG-005** SHOULD: Use a shared event buffer abstraction (e.g., EventOptimizer class) that can be reused across different data access components to maintain consistency.

- **R-EVLOG-006** SHOULD: Implement periodic flush intervals on application lifecycle events (beforeunload, visibility changes) to mitigate log data loss during crashes.

- **R-EVLOG-007** MAY: Consider using Web Workers or similar background threads for log processing in browser environments to avoid blocking the main thread.

### Verify

```bash
# Count event buffer and logging buffer implementations
grep -r "eventOptimizer\|EventBuffer\|LogBuffer" --include="*.ts" --include="*.js" | wc -l

# Count flush and batch logging patterns
grep -r "flush.*log\|batch.*log" --include="*.ts" --include="*.js" | grep -v "node_modules" | wc -l

# Run logging and buffer tests
npm test -- --grep "logging.*buffer\|event.*batch" 2>&1 | grep -E "passing|failing"
```

**Accept when:**
- All data access operations in performance-critical paths use buffered logging mechanisms rather than synchronous writes
- Event buffer implementations include configurable flush intervals and maximum size limits
- Log events include structured metadata (timestamps, correlation IDs, operation context) sufficient for distributed tracing
- Tests verify that logging does not block data access operations and that buffers flush correctly on lifecycle events
- No synchronous logging calls are detected in data access paths via automated code review
- Performance tests confirm logging overhead does not exceed 5% of operation time

Claude Code MUST NOT skip or defer verification of these rules. Violations in performance-critical data access paths MUST trigger CI build warnings and code review rejection. Performance regression alerts MUST be raised if logging overhead exceeds defined thresholds.
</enforcement>
