<rule_activation id="72fd0af9-19bc-43c3-8437-d33d2ce414c6" title="Adopt Event-Driven Logging with Buffered Batch Processing for Data Access Operations: Logging Implementations Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching `**/*`. Logging implementations in data access operations, browser extensions, real-time streaming, and connection management MUST use buffered batch processing to avoid blocking performance-critical paths.
</rule_activation>

### Rules

- **R-EDLBBP-001** MUST: Logging implementations MUST use buffered batch processing to avoid blocking data access operations.

### Verify

```bash
# Count event buffer and log buffer implementations
grep -r "eventOptimizer\|EventBuffer\|LogBuffer" --include="*.ts" --include="*.js" | wc -l

# Count flush and batch logging patterns
grep -r "flush.*log\|batch.*log" --include="*.ts" --include="*.js" | grep -v "node_modules" | wc -l

# Run logging and buffer tests
npm test -- --grep "logging.*buffer\|event.*batch" 2>&1 | grep -E "passing|failing"
```

**Accept when:**
- All data access operations in performance-critical paths use buffered logging mechanisms rather than synchronous writes
- Event buffer implementations include configurable flush intervals and maximum size limits
- Log events include structured metadata (timestamps, correlation IDs, operation context) sufficient for distributed tracing
- Tests verify that logging does not block data access operations and that buffers flush correctly on lifecycle events

<enforcement>
Claude Code MUST NOT skip or defer verification. Violations of R-EDLBBP-001 in performance-critical data access paths MUST be flagged during code review and rejected in CI pipeline. Performance regression alerts trigger if logging overhead exceeds 5% of operation time.
</enforcement>
