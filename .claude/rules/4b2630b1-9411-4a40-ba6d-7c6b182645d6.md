<rule_activation id="4b2630b1-9411-4a40-ba6d-7c6b182645d6" title="Standardize Environment Variable Configuration Management Pattern: Configuration Modules Provide" applies_to="**/*">
These rules are ALWAYS ACTIVE for all configuration and environment management code across the codebase.
</rule_activation>

### Rules

- **R-CONFIG-001** SHOULD: Configuration modules SHOULD provide default values for non-critical environment variables.

### Verify

```bash
# Verify all direct process.env accesses are contained within designated configuration modules
grep -r 'process\.env' --include='*.ts' --include='*.js' --exclude-dir=node_modules | grep -v 'common.ts\|config.ts\|env.ts' | wc -l

# Count configuration modules with process.env access
find . -name 'common.ts' -o -name 'config.ts' -o -name 'env.ts' | xargs grep -l 'process\.env' | wc -l

# Check for ESLint violations of no-process-env rule
npm run lint -- --rule 'no-process-env: error' 2>&1 | grep -c 'process.env'
```

**Accept when:**
- All direct process.env accesses are contained within designated configuration modules (common.ts, config.ts, env.ts)
- Each package with environment dependencies has a dedicated configuration module with typed exports
- Linting rules successfully detect and flag any direct process.env access outside configuration modules
- Configuration modules export typed constants or objects rather than functions when possible
- Required vs. optional environment variables are documented in package README files

<enforcement>
Claude Code MUST verify that all environment variable access follows the centralized configuration pattern. Violations detected by grep or linting commands MUST block acceptance. Code review MUST confirm configuration modules are properly typed and documented.
</enforcement>
