<rule_activation id="8b732717-798d-4c64-a4a1-8532e5d8a589" title="Adopt IndexedDB as Client-Side Cache Layer for Logging and State Persistence: Cache Implementations Implement" applies_to="**/*">
These rules are ALWAYS ACTIVE for all client-side applications, Chrome extensions, browser-based tools, Progressive Web Applications (PWAs), and client-side logging/caching implementations.
</rule_activation>

### Rules

- **R-INDEXEDDB-001** SHOULD: Cache implementations SHOULD implement automatic cleanup policies (TTL, size limits) to prevent unbounded storage growth.

### Verify

```bash
# Verify IndexedDB usage patterns in client-side code
grep -r "indexedDB\|IndexedDB\|IDBDatabase" apps/ packages/ --include="*.ts" --include="*.tsx" --include="*.js"

# Verify database operations and transactions
grep -r "openDatabase\|createObjectStore\|transaction" apps/ packages/ --include="*.ts" --include="*.tsx"

# Run tests for IndexedDB, cache persistence, and logging storage
npm test -- --grep "IndexedDB|cache.*persist|logging.*storage"
```

**Accept when:**
- All client-side logging and caching implementations use IndexedDB utilities with proper async/await error handling
- IndexedDB implementations include cleanup policies and quota management mechanisms
- Code review confirms no synchronous localStorage usage for large data or logging purposes in browser extension contexts
- Automatic cleanup mechanisms are implemented using periodic background tasks that remove old entries based on timestamp or enforce size limits
- IndexedDB utility module encapsulates database initialization, schema versioning, and common CRUD operations

<enforcement>
Claude Code MUST NOT skip or defer verification. All client-side caching and logging implementations MUST comply with R-INDEXEDDB-001. Pull requests using localStorage for large data or logging are flagged for review. Violations trigger automated comments suggesting IndexedDB utility migration. Repeated violations require architecture team review and justification.
</enforcement>
