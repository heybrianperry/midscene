These rules are ALWAYS ACTIVE for all files matching public API client implementations, visualizer, playground, and blackboard component code.
</rule_activation>

### Rules

- **R-CACHE-001** SHOULD: API responses SHOULD include cache control headers (Cache-Control, ETag, Last-Modified) to guide client-side caching behavior.
- **R-CACHE-002** SHOULD: Use a storage provider abstraction layer (e.g., indexeddb-storage-provider) to enable swapping storage backends without changing consumer code.
- **R-CACHE-003** SHOULD: Implement cache keys using a consistent naming convention: 'api:version:endpoint:params' to avoid collisions.
- **R-CACHE-004** SHOULD: Include cache metadata (timestamp, version, TTL) alongside cached data for effective invalidation.
- **R-CACHE-005** SHOULD: Provide developer tools or debug modes to inspect, clear, and monitor cache state during development.
- **R-CACHE-006** SHOULD: Consider using libraries like idb-keyval or localforage to simplify IndexedDB interactions and provide fallbacks.
- **R-CACHE-007** MUST: Implement cache versioning, TTL enforcement, and manual cache clear functionality to mitigate cache invalidation bugs.
- **R-CACHE-008** MUST: Implement storage quota monitoring, automatic cache pruning of oldest entries, and graceful degradation to network-only mode.
- **R-CACHE-009** MUST: Implement encryption for sensitive cached data, exclude authentication tokens from cache, and provide clear security guidelines.

### Verify

```bash
# Verify IndexedDB, localStorage, or sessionStorage usage with cache/storage patterns
grep -r 'IndexedDB\|localStorage\|sessionStorage' packages/*/src --include='*.ts' --include='*.tsx' | grep -i 'cache\|storage\|provider'

# Verify cache TTL and expiration logic
grep -r 'cache.*TTL\|time.*to.*live\|expir' packages/*/src --include='*.ts' --include='*.tsx'

# Verify storage provider abstractions and cache interfaces
grep -r 'class.*StorageProvider\|interface.*Cache' packages/*/src --include='*.ts' --include='*.tsx'
```

**Accept when:**
- All public API client implementations include a documented cache layer using browser storage APIs
- Cache implementations include explicit TTL configuration and invalidation logic
- Storage provider abstractions exist to decouple cache implementation from consumer code
- Cache control headers (Cache-Control, ETag, Last-Modified) are present in API responses
- Cache metadata (timestamp, version, TTL) is stored alongside cached data
- Sensitive data is encrypted or excluded from client-side cache
- Storage quota monitoring and graceful degradation mechanisms are implemented
